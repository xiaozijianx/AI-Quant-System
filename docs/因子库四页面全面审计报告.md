### 2.2 计算机制: 复合因子能否直接算?(核心结论, 已 DB 实测)

**你的理解是对的, 需要修正此前报告的表述**:

- **DB 实测**: 74 个复合因子的 formula **全部是"基类实例组合"形式**, 如 `returns(21)`、`adx(14)*rsi(14)`、`macd()*adx(14)`、`-1*ts_Decay(...)`。**没有任何一个 formula 直接引用"其他因子 ID"**(如 `ret_1d + vol_ratio_10d` 这种)。
- **计算机制**: [calc_factor](file:///e:/jikeAI/code/CASE-AI量化系统/lib/factor_engine.py#L4595) → `evaluate_expression` 求值时, 命名空间注入 [BASE_OPERATOR_MAP](file:///e:/jikeAI/code/CASE-AI量化系统/lib/factor_engine.py#L4354) 的基类可调用函数(`returns(1)` → `ts_PctChange(Close,1)` 等)。**等价于"递归读取基类的计算方式再求值"**——只是实现为求值期动态展开, 而非预先还原成完整公式。
- **因此**: 复合因子**能计算**, 但前提是公式引用的是"基类实例"(BASE_OPERATOR_MAP 内), 而不是"自定义因子 ID"。
- **构建页的行为印证**: [bldInsertFactor](file:///e:/jikeAI/code/CASE-AI量化系统/templates/factor.html#L4102-L4107) 把"全部因子"面板的因子拖入表达式时, 插入的是 **`f.formula`**(该因子的基类公式), 再 `bldParse` 成块, **不是引用因子 ID**。即"复合因子被递归展开成基类公式再拼装"——正是你说的"读取基类的计算方式递归计算"。

> **隐含约束(需你知晓)**: 命名空间不含"其他因子 ID", 所以**自定义因子若公式直接写 `ret_1d + vol_ratio_10d`(引用因子ID) 会 NameError 算不了**; 正确写法是基类形式 `returns(1) + volume_ratio(10)`。构建页面已天然规避(拖入=展开公式), 但手工编辑表达式时需注意此约定。这**不是 bug, 是设计约定**, 建议在构建页/文档中明示。

### 2.3 计算性能(选很多因子时)

**瓶颈(已核实)**: `_talib_panel_apply` 逐股 for 循环调 TA-Lib; `ts_Decay*` 用 rolling.apply+lambda; `evaluate_expression` 每次重算 `_build_field_dfs`; `neutralize_regression` 逐列逐期 OLS; `evaluate_pattern_factor` 逐股逐日循环; `_multi_period_correlation` 每期 O(n²) 相关; `build_marketcap_proxy_map` 每期逐股重算。

**优化方案(不改结果口径)**: `_build_field_dfs` 按(panel指纹,字段集)LRU 缓存(收益最高) → TA-Lib 按列批量 → `neutralize_regression` 合并 OLS → `ts_Decay` 改 numpy 卷积 → `build_marketcap_proxy_map` 一次性滚动。

**✅ 已实施(2026-08-16, 详见十-阶段三)**, 五项优化全部落地并验证一致性+提速(见十-阶段三 / 十一)。其中 `neutralize_regression` 在实施中发现**隐藏真问题**: Agu-2 生产环境未安装 statsmodels, 原实现 import 失败静默回退 zscore, 导致"分组/市值中性化"从未真正生效; 已用 numpy 显式拼接常数项 + lstsq 求残差彻底去依赖(与 OLS 数学等价, base 环境 statsmodels 交叉验证残差 < 1e-8)。

### 3.2 四分类是否合理

- **financial**: 低频季度数据, 财报可用日(report_date+分级滞后120/90/45)对齐调仓, asof 前向填充防未来函数 —— **合理**。
  - **滞后判断机制(用户关注点, 已核查)**: 不是按"实际披露日"(表里没有 announce_date), 而是按**报告期类型**取"监管最迟披露期限"作为保守数据可用日:
    - 判断依据: `_report_lag_days` 按 **report_date 的月份** 识别报告期类型 —— 12月期(年报)→120天(次年4月底)、6月期(半年报)→90天(8月底)、3月/9月期(一季报/三季报)→45天(4月底/10月底)、其余月份→90天保守。
    - 即"能明确判断是哪个季报"(按 report_date 月份), 并按该季报的最迟披露期限滞后 —— 与你设想的"知道是一季报就按一季报最迟截止时间延迟"完全一致。
    - **是否考虑披露时间不准确性**: 用的是"监管最迟期限"(保守, 绝不提前用未来数据, 安全), 而非"实际披露日"(更精确但表里无此字段)。后果: 实际披露早于最迟期限的公司会被"多滞后"几天, 损失时效但不泄露未来; 若后续能拿到实际披露日(announce_date), 可改为 `实际披露日 + 1~2日` 提升时效(建议项, 非 bug)。
- **technical**: 连续截面可比 —— 合理。
- **signal**: 离散/稀疏/方向语义, 事件信号评价而非 IC —— **合理**, 双极性(CDL±100)按值符号、单极性(新高/新低)按 direction。
- **technical_ts**: 价格水平/累积量纲/绝对波动类(均线绝对值/价格变换/OBV/STDDEV 等 19 个)先滚动分位再入截面 —— **合理**, 不改公式只改评价预处理, 窗口自适应降窗已修复。

### 3.3 评价覆盖度

- 四类均有完整评价管线, 全部可产出可解释结果。
- `none`(约22): 构造中间字段/待配引擎, 评价时**显式列出**, 不静默跳过 —— 已处理。
- D 组文字化因子(缠论买卖点/微观结构/龙头, 缺引擎): 批量评估中静默跳过, 待配引擎 —— 已知遗留(用户自行推进)。

## 四、多因子分析页面(Tab6)(重点)

### 4.1 流程

**B1**(`prep_multi_factor`): 调仓日序列 → 逐期截面 → 统一预处理(3×1.4826×MAD + 中位数填充 + 分组/市值回归中性化 + Z-score) → 未来收益。**与合成方式无关**, 缓存复用。
**B2**(`synth_multi_factor_eval`): 阶段A 全历史 IC 筛选+相关性去冗余+初始方向; 阶段B walk-forward 主循环(方向/IC权重/ML 训练均只用当期之前)。

### 4.2 异类因子融合(用户核心关切: 会不会磨灭因子特点)

| 类型 | B1 融合 | 是否磨灭特点 | 判定 |
|---|---|---|---|
| technical | 连续截面统一预处理 | 否 | 合理 |
| technical_ts | 先时序分位化再入截面 | 否 | 合理 |
| financial | asof 对齐 + 逐日前向填充入连续截面, 与连续因子一起 MAD/中性化/Z-score | 轻微: 财务低频, **中位数填充**会掩盖缺失样本信息(近2年可用率高, 实际影响小) | 基本合理, 建议观测填充占比 |
| signal | **独立轨**(方向得分+多信号等权平均+混合0.5叠加/signal_only整轨), **不进连续截面** | **否, 完全保留信号方向语义** | 合理, 正是为"不磨灭信号特点"设计 |

**结论**: 架构层面已避免"清洗磨灭信号特点"(信号独立轨); 财务中位数填充是唯一需观测点。

### 4.3 中性化/加权/后处理(对照三 case)

- 中性化: 分组+市值可叠加, 统一回归残差+再Z-score(对齐 CASE-C/ML case); 市值用点-in-time 近20日均额代理, 规避静态市值前视。
- 加权: walk-forward IC 加权(滚动历史, 非当期)对齐 CASE-C 正确版; Markowitz/Optuna 用当期之前历史; ML 累积历史+周期重训+purged CV(gap 按每期截面行数自适应)对齐 ML case。
- 后处理: PerformanceWithCost(延迟2日+成本)、Top-N 对比(含基准)、Calmar/月度胜率/多空/L5-L1 —— 对齐清华/网格。
- **差距收敛**: 清华 Barra 暴露/风险分解/组合中性化(F1)已补齐; 网格等权/多因子对比已覆盖; ML walk-forward+purged CV 已对齐。

### 4.4 因子包: 异类因子能否都放进一个包(最终目的: 综合评分)

**能, 已闭环**: 保存时 `build_final_use_from_prep` 全历史定 `factor_ids/weights/direction/ml_model_path/pca_model_path`, `__signal_combo__` 映射回真实信号ID, `ts_normalize_window` 随包; 消费端 `score_stocks_by_package` 分轨处理(technical_ts 分位化/signal 独立轨/连续统一预处理, 混合 = 连续综合 + 0.5×信号), 产出每股综合分。**生成→消费三口径(technical_ts/signal/预处理)已对齐**。

### 5.2 试算与保存自动识别

## 八、总体结论

- **工程骨架与设计意图高度一致**: 因子公式自包含(基类实例形式), 求值靠基类展开, 复合因子可算; 评价按四类分型(财务/技术/形态/technical_ts)+none 显式兜底; 多因子异类融合"连续统一预处理 + 信号独立轨"从设计上避免磨灭信号特点; 因子包把异类因子统一进一个包并给出综合分, 生成→消费三口径已对齐; 构建页块式编辑(拖入因子=展开基类公式) + 自动识别保存闭环完整。
- **无未来函数控制总体到位**, 主要残留是 B2 阶段A 全历史筛选的选择前视(评价口径, 非阻塞)。
- **本轮确认并修复 1 个真实 bug**(信号多信号平均不等权); 其余为低危/优化/清理项。
- **2026-08-16 死代码清理**: 已删除 `/multi_factor_eval`(引擎函数保留)、`/generate`、`/construct` 三处冗余路由及前端 `generateFactor`/`testExpression`/`updateGenPreview` 死方法与相关状态; 路由注册与前端 JS 语法均已验证(见十/十一)。
- **2026-08-16 计算性能优化**: 五项优化落地(`_build_field_dfs` LRU 缓存/`ts_Decay*` 卷积/`_talib_panel_apply` 预提取/`build_marketcap_proxy_map` 面板缓存/`neutralize_regression` 去 statsmodels), 11 项一致性验证全过, 性能提速(ts_Decay 约 1039x、字段面板缓存约 14x); 附带修复 neutralize_regression 因 Agu-2 缺 statsmodels 静默回退 zscore 导致"分组/市值中性化"从未生效的隐藏真问题(见十-阶段三)。
- **最重要的隐含约束**(需你在文档/构建页知晓): 因子公式必须引用基类实例而非自定义因子 ID, 否则引擎无法解析(命名空间无因子ID)。这是设计约定, 不是 bug, 但应在构建页提示, 避免用户手工写 `ret_1d + vol_ratio_10d` 报错。

> **B2 阶段A 全历史 IC 筛选说明**(用户问"什么意思/为什么偏乐观/原本应怎样"):
> - **是什么**: 多因子合成主循环(阶段B)之前, 阶段A 先对每个因子算出**整段评价期的 IC 时序**(`factor_full_ic`), 再用**全历史 IC** 做两件事——①筛选(`_screen_factors`: |IC均值|低于阈值淘汰、非空率/覆盖率不足淘汰)②去冗余(`_redundancy_remove`: 两两相关>0.8 保留 |IC| 更高者)。决定"哪些因子进合成"的依据, 是**整个样本期**的 IC。
> - **为什么偏乐观**: 用同一段样本**既选因子、又评因子** → 被选中的因子天然是这段时期表现好的(样本内选择偏差/数据窥探)。合成后的组合 IC/IR 往往高于"真实前视外推"能拿到的水平。这是选择偏差, 不是未来函数——方向/权重/ML 训练都是 walk-forward(只用截至当期之前的数据), 只有"选哪些因子"用了全历史。
> - **原本应怎样**: 严格 walk-forward 应**逐期选因子**(每个调仓点只用当期之前的历史 IC 决定因子取舍), 但那样选择本身波动大、实现复杂, 且选因子不是本评价要回答的问题。
> - **取舍**: 现设计是**评价口径**(回答"假设事后知道这组因子表现, 组合有多好", 用于因子间横向比较), 已用 `screening_caveat` 在"二、因子筛选"面板顶部标注"展示指标可能偏乐观"; 严格的单因子逐一验证请走单因子评价。**本轮不改筛选逻辑**(符合用户"保持+已标注"决定), 仅保留说明。
