## 1. 背景与目标

### 1.1 现状 (草稿, 将抛弃)

因子库页面 Tab3「因子挖掘」目前有**两个子页**(`templates/factor.html` L699-819, 后端 `routes/factor.py` L411-603):

| 子页 | 接口 | 现状 | 处置 |
|------|------|------|------|
| SVD 隐因子 | `POST /mine_svd` | 收益率矩阵去均值 → SVD → 展示方差解释 + 暴露表 | 降级为辅助诊断 |
| ML 特征重要性 | `POST /mine_ml` | 12 个基础因子, 每股 1 快照, 展示特征重要性 + 样本内 R2 | 抛弃 |

草稿的根本缺陷:
1. 只"诊断展示", 不产出新因子, 不落库。
2. `mine_ml` 每股只取 1 个快照(样本 ≤ 100), R2 为样本内虚高值, 无统计意义。
3. `mine_ml` 的特征诊断功能 **多因子页已具备**(ML 合成分支内置 `_extract_feature_importance` + `importance_feedback`, 前端 L1642-1661 已展示"ML 特征重要性"和"按重要性筛选并重训"按钮)。继续做"特征诊断"页 = 与多因子页重复。
4. `mine_svd` 缺投影机制、缺经济解读, 仅可作市场状态诊断。

### 1.2 挖掘页的真正定位

> **因子挖掘页 = 因子库外的新因子自动生成器。**

目标: 用机器学习在"字段 × 算子"的表达式空间里**自动搜索、生成新的因子表达式**, 经评价后**注册进因子库**, 供多因子页/晨会等消费。这是它与多因子页、因子构建页**不重复的本质原因**:
- 多因子页只消费**因子库已有因子**(合成选股);
- 因子构建页只能**人工**拖拽构造;
- 挖掘页是**程序自动**发现**库外**的新表达式。

### 1.3 关键事实 (来自代码核实)

1. **50+ 宽特征已全部被因子库覆盖**: `factor_init.py` 的价量/动量/波动率/技术指标/形态/交互六类因子, 注释明确"来源: ml_strategy/feature_engine.py", 与 `feature_engine.py` 的 50 个特征 factor_id 一一对应。因此"用 ML 在宽特征上做预测" ≠ 因子挖掘(多因子页选满 50 个因子即可复现), 不是挖掘页的立足点。
2. **多因子页 ML 已实现特征诊断 + 重训 + 综合因子 + 评价 + 因子包**完整闭环(factor_engine.py L3455-3474, L3564-3585), 且前端已展示。挖掘页无需重复该能力。
3. **因子构建页已定义表达式语法与引擎**(字段 + 算子 + 参数, 可解析可执行) —— 这恰好构成 GP/RL 搜索所需的"终端集 + 函数集 + 适应度评估器"。
4. **所有 CASE 均无"随机生成因子"能力**: 清华 CF_lgb 是"手工预设少量公式 → ML 预测 → 预测值转因子再评价", 是公式化 Alpha 的演示, 不是自动生成。业界真正的自动生成需引入 GP/RL/LLM(见第 2.6 节)。

## 2. 调研结论 (参考来源)

### 2.1 CASE-机器学习因子挖掘 / 主系统 ml_strategy

- 特征工程: 6 大类 50+ 特征(价量/动量/波动率/技术指标/均线形态/交互), 已被因子库覆盖。
- 标签/训练/验证: `make_labels`(未来 N 日收益) / `rolling_train_predict`(walk-forward) / `purged_kfold_cv`(gap 防泄漏) / `evaluate_factor`(预测概率当因子算 IC/ICIR/分层)。
- **借鉴点**: walk-forward + purged CV 的防泄漏框架, 可复用于"候选因子批量评价"(评价候选时只用历史数据, 避免未来函数)。

### 2.2 CASE-网格与多因子 (8-ML增强多因子.py)

- 特征: 技术因子 + 交互特征, 月末截面构造, LightGBM 预测未来 20 日收益排序选股。
- **借鉴点**: 与多因子页 ml_reg 同构, 属"体系外草稿", 仅佐证多因子页 ML 已足够。

### 2.3 CASE-QuantStats (2-SVD因子挖掘与分析.py)

- 完整 SVD 分析: 收益率矩阵去均值 → SVD → 方差解释/累计方差定因子数 → 暴露解读 → 隐因子时序 → 滚动 SVD → 降维 → 残差分析。
- **定位**: 保留为挖掘页的**辅助诊断**(市场状态/隐因子/残差), 不再是主功能。

### 2.4 qinghua (清华量化课程)

- 因子构造: `ts_Delay/Mean/Decay/Stdev` 等算子 + `pn_TransNorm` 构造因子公式, 批量检验。
- 因子评价: `GetRets`(IC 时序) / `GetQuantileRet`(分位收益) / `PerformanceWithCost`(含成本多空收益)。
- ML 落点: `gl23_day2_M.ipynb` 用 LightGBM 预测未来 20 日收益 → 预测值转因子 CF_lgb → ts_Decay → PerformanceWithCost 评价。
- **关键结论**: 清华的 f1~f5 是**手工预设公式**, **无随机生成因子能力**; 其"预测转因子再评价"闭环 = 多因子页 ml_reg 已实现的等价物, 无需为 CF_lgb 单独建功能。
- **借鉴点**: 因子公式的算子风格(ts_* + 截面算子 + 字段)与因子构建页表达式语法一致, 是 GP 搜索空间设计的直接参照。

### 2.5 主系统已有的可复用设施

- 表达式引擎(`lib/factor_engine.py`): 解析并执行 `ts_Mean(Close,5)`、`rank(x)`、`returns(1)`、`amplitude(5)` 等, 是 GP/RL 候选表达式的**评估器**。
- 因子构建页(`factor.html` 拖拽编辑器 + `/trial` 试算 + `/save` 保存): 已定义"字段 + 算子 + 参数"的合法组合空间与入库通道。
- 因子库(`factor_library`, `upsert_factor`): 新因子注册入口。
- 因子评价(`factor_evaluator`, evaluation_type 路由, IC/分层/PerformanceWithCost 等价物): 候选因子批量评价。
- 单因子/多因子分析页: 新因子入库后的正式评价与合成消费。
- 股票池(`get_pool_stocks`) / 行情(`load_daily_kline`) / JSON 安全(`_json_safe_response`)。

### 2.6 业界"自动因子挖掘"方法 (网络调研 2026-08)

| 方法 | 做法 | 输出 | 代表 |
|------|------|------|------|
| 遗传编程 GP | 字段×算子随机组合成表达式树, IC/IR 做适应度, 进化(选择/交叉/变异)筛选 | 可读表达式 | gplearn、Warm-Start GP、alpha-mining-system |
| 强化学习 RL | 表达式 Token 化(逆波兰)成序列, 每步选算子/窗口/字段, IC 当奖励训练策略 | 可读表达式 | AlphaForge、AlphaQCM、Hierarchical RL |
| 深度网络 AlphaNet | 原始行情 → 神经网络 → 直接输出 alpha(黑箱嵌入) | 不可读黑箱因子 | 华泰 AlphaNet / Qlib |
| LLM 生成 | 大模型直接写因子公式(可配 MCTS 搜索) | 可读表达式 | AlphaGPT、QuantaAlpha、清华 Alpha Jungle |

- **共同范式**: "字段 + 算子 + 表达式 + 回测"的生产范式(东方证券《大语言模型驱动因子挖掘的模型演进》)。
- **GFlowNet**(生成流网络): 以"生成一群低相关、多样化的优秀公式"为目标, 相关性中位数 <0.04, 显著优于 RL 的多样性(2026-05 中文报告)。
- **Mega-Alpha 合规路径**: 业界把大量 alpha 因子收进因子库, 用组合模型合成 Mega-Alpha(AlphaForge)。前提: 每个 alpha 先 OOS 验证 + 因子间去冗余(相关性>0.8 剔除) + 捕捉增量信息。

#### 2.6.1 遗传编程(GP)因子挖掘代表案例 (网络调研 2026-08)

| 案例 | 技术要点 | 与我们系统的对应关系 |
|------|----------|----------------------|
| **gplearn**(trevorstephens/gplearn) | 最成熟的 Python GP 库(scikit-learn 风格): 表达式树 + `make_function` 自定义函数集 + `make_fitness` 自定义 IC 适应度; 锦标赛选择 + 子树交叉 + 点变异; parsimony_coefficient 复杂度惩罚 | 进化结构(选择/交叉/变异/精英)可直接借鉴; 但其函数签名是"特征矩阵 X→标量", 与我们的"面板 DataFrame + 逐股 rolling"语义不匹配, 不建议强套 |
| **QuantGplearn**(WYFHHH/QuantGplearn, 2026-06) | 面向量化因子的 GP 框架: 行情特征 + 时序算子(ts_zscore/ts_delta 等) + 截面算子(cs_rank/cs_demean)组成可读表达式; NumPy/Pandas 与 Torch GPU 双后端, 支持 `[时间,标的,特征]` 面板 | 其算子风格(ts_*/cs_*)与我们的因子构建 DSL 几乎同构, 印证搜索空间设计方向正确 |
| **Auto-Alpha-Finding**(sw0843) | gplearn 挖因子 + **残差正交化**(新因子强制与已有因子池正交, 保证增量 alpha) + 相关性过滤 + walk-forward 回测 + 因子组合优化 | 残差正交化/去冗余 = 我们多因子页 `_redundancy_remove`(Spearman>0.8 剔除)的同类思想, 用于挖掘页 Top-N 候选去冗余 |
| **AutoAlpha**(清华, arXiv:2002.08245) | **分层搜索**(hierarchical)快速定位有前景区域 + **PCA-QD**(基于主成分的多样性引导) + **warm start + 替换机制**防早熟 | 分层初始化与 PCA 多样性引导作阶段3 增强; warm start 直接吸收"库内已有因子表达式" |
| **Warm-Start GP**(Ren et al., arXiv:2412.00896, 2024) | 标准 GP 在巨大搜索空间效率低 → 聚焦"有前景区域": **精心初始化**(用已有 alpha 基因) + **结构约束** + IC 适应度, 2020-2024 A 股 OOS 优于基准 | 直接支撑"基础因子/参数化模板作为初始基因"的 Warm-Start 方案(见 4.6) |
| **LLM 增强 GP**(东吴金工, 2026-05) | LLM 提取"子表达式基因" → 构建树搜索空间 → **分岛进化** + 周期 LLM 注入 + 低相关筛选; 87 候选全区间\|RankIC\|均值 6.98%, ICIR 0.79, 81.6% 因子对相关<0.70 | LLM 作"基因供给 + 多样性注入"的增强手段, 列入阶段5 备选 |
| **CSDN 多因子 GP 案例**(2024-04) | gplearn 自定义算子 + 自定义 IC metrics 挖因子, 单因子测试 + 多因子选股回测(年化 23.6%, 夏普 5.87) | 印证"IC 当适应度 + 单因子测试"闭环可行; 参考其自定义 metric 写法 |
| **中金/光大 GP 研报**(mbalib 收录) | 解析 alpha101 拆出基本函数与算子, 用 DEAP 实现 GP 再挖掘; 算子含 ts_sum/ts_max/rank/delta/correlation 等, 控制树深度/复杂度 | DEAP 参数(种群/代数/交叉变异概率)与我们的 GP 参数面板对应 |

#### 2.6.2 业界 GP 核心设计共识 (落地依据)

1. **表达式 = 树**: 终端集 = 字段/常数, 函数集 = 算子; 我们直接用因子构建 DSL 的字段+算子作为终端/函数集, 保证生成结果"构建页可打开、因子库可入库"。
2. **适应度 = IC**: 最常见适应度是截面 RankIC 均值(可选叠加 ICIR/分层多空/夏普); 我们复用 `run_ic_timeseries_panel`。
3. **防过拟合三件套**: 复杂度惩罚(parsimony) + 训练/验证分段(OOS) + 去冗余/多样性(相关性>0.8 剔除, PCA-QD / 低相关奖励)。
4. **Warm Start 是标配**: 纯随机初始化在"有效 alpha 稀疏"的搜索空间效率极低(AutoAlpha / Warm-Start GP 共同结论), 用已有因子表达式注入初始种群是标准做法。
5. **结构约束**: 深度上限 + 参数域离散化(窗口取 {3,5,10,20,60,120,250} 等有限集合)大幅压缩搜索空间。

## 4. 功能 A: 自动因子生成(主功能, 全新)

### 4.1 输入

> v3: 本节与 4.2 以 GP 主引擎为准(阶段 1~5 唯一推进对象); RL/LLM 引擎的输入差异见阶段 6。

- 股票池 + 时间区间(同页面现有下拉)。
- 字段集: 复用因子构建页的原始字段(Open/High/Low/Close/Volume/VWAP 等, 以引擎支持为准)。
- 算子集: 复用因子构建页的运算符(加减乘除) + 时序算子(ts_Mean/ts_Decay/ts_Delay/ts_Std 等) + 截面算子(rank/quantile 等), 以引擎支持为准。
- 搜索参数: 种群大小/代数/表达式深度上限(GP), 或 Token 集/序列长度(RL), 或 LLM prompt。
- 评价参数: 持有期 horizon、IC 方法(Pearson/Spearman)、去极值口径、是否中性化。

### 4.2 流程 (GP 主引擎, 其他引擎共用骨架见阶段5)

1. 初始化种群: 从字段集+算子集随机组合生成 N 个候选表达式(约束: 语法合法 + 深度/复杂度上限)。
2. 候选评价: 对每个候选表达式用**表达式引擎**计算因子值 → 在股票池×时间上计算 IC/IR/分层收益(复用 factor_evaluator; 用 walk-forward/分时段评价防未来函数)。
3. 适应度: IC 均值 / ICIR / 分层单调性(可叠加低相关性奖励, 参照 GFlowNet 的多样性目标)。
4. 进化: 选择(锦标赛/轮盘赌) → 交叉(子树交换) → 变异(算子/字段/常数替换) → 新一代。
5. 终止: 达到代数上限 → 输出 Top-N 候选(按适应度排序)。
6. 去冗余: 对 Top-N 候选两两算 Spearman, 剔除相关性>0.8 的冗余组(保留 IC 更高者, 复用多因子页去冗余思路)。
7. 展示 + 入库: 候选列表(表达式/IC/IR/分层/与库内因子相关性) → 用户勾选 → `upsert_factor` 注册进因子库。

### 4.3 引擎选型(建议优先级)

> v3 收敛: GP 为当前**唯一推进**的主引擎(阶段 1~5); RL / LLM 增强 / GFlowNet 为**其他引擎**, 推迟到阶段 6 及以后作为独立子页备选。

| 引擎 | 优先级 | 理由 | 落地方式 |
|------|--------|------|---------|
| 遗传编程 GP | **首选(阶段1~5)** | 实现最简单、可解释、先跑通"生成→评价→入库"闭环 | **已落地**: 以 QuantGplearn 的进化循环为骨架(见 4.6.1 选型逻辑), 自写轻量内核(`lib/factor_gp.py`), 表达式生成与适应度复用现有引擎(CPU 路径)/同构 QuantGplearn 张量语义(GPU 路径, 见 4.6.2/5.4.1); 不引入 gplearn/sklearn 依赖(见 4.6.3) |
| 强化学习 RL | 阶段6备选 | 搜索质量更高但复杂、训练成本高 | 表达式 Token 化(RPN) + PPO, IC 当奖励; 需 GPU/较长训练 |
| LLM 增强 GP | 阶段6备选 | 可解释性好、基因供给 + 多样性注入(东吴金工思路) | 分岛进化 + LLM 周期性注入子表达式基因 + 低相关筛选(见 4.6.4) |
| GFlowNet | 远期 | 多样性最优但实现最重 | 暂列远期规划 |

### 4.4 输出

| 输出 | 内容 | 展示 |
|------|------|------|
| 候选因子表 | 表达式 / IC均值 / ICIR / 分层 / 与库内因子最大相关 | 表格(可排序、可勾选) |
| 进化曲线 | 每代最优/平均适应度 | 折线图 |
| 去冗余报告 | 冗余组及保留项 | 提示 + 表格 |
| 入库结果 | 勾选因子保存状态(factor_library) | 保存成功提示 |

### 4.5 产出对接

- **注册因子库(主出口)**: 勾选候选 → `upsert_factor` 写入 `factor_library`(含 formula/表达式, evaluation_type 按表达式推断或 `_is_technical_ts_expression` 启发式标记) → 出现在因子库 Tab1 → 可进单因子/多因子评价。
- **保存因子包(可选)**: 若候选就是"模型预测综合因子"(见第 6 节), 可走多因子页已有 `POST /package` 存为 ml_cls/ml_reg 因子包。
- **持久化**: 挖掘任务与候选结果持久化(新增 `factor_mine_result` 表或复用 `factor_eval_result`), 刷新后恢复。
- **页面状态持久化(前后端解耦, 多实例共享)**: 因子库页面的前端状态(当前Tab/选中因子/筛选/GP参数, 含任务 8/9 的 `gpReplacement`/`gpReplacementThresh`/`gpHierarchical`/`gpFitnessMode`)统一存后端 `agent_data/ui_settings/factor_page.json`(经 `/api/page-settings/factor_page` GET/POST), 不在浏览器 localStorage 保存。任意端口/多个实例打开同一后端, 都能读到同一份参数配置; 保存采用"唯一临时文件 + os.replace 原子替换 + 短重试", Windows 下多实例并发写不损坏 JSON。

### 4.6 搜索空间(输入端)分级评估

**核心结论: 不应把所有算子 / 基础因子 / 参数化模板一次性放进 GP 搜索空间** —— 会指数级膨胀且大量候选无意义。按"字段 → 算子 → 基础因子"三级分层 + 结构约束控制。代码核实依据: `factor_engine.py` 的 `_SAFE_FIELDS`(字段)、`_SAFE_FUNCTIONS`(ts_*/cs_*/ta_* 算子)、`BASE_OPERATOR_MAP`(参数化基类)、`routes/factor.py` 的 `OPERATORS`/`FIELDS`。

| 层级 | 内容 | 规模 | 是否纳入 |
|------|------|------|---------|
| L0 字段(终端) | Open/High/Low/Close/Volume/Amount/VWAP/Turnover | 8 | 是(首版) |
| L0 常数(终端) | {0,1,2,3,5,10} 少量整数常数 | 6 | 是(让 GP 能发现缩放/偏移) |
| L0 算术(函数) | + - * / abs sign log | 7 | 是 |
| L0 时序(函数) | ts_Delay/Mean/Decay/Max/Min/Delta/Stdev/Sum/Median/PctChange/ROC/Amplitude/VolRatio/HistVol/Bias/Log/Corr/Cov | 18 | 是(首版核心, 覆盖 90% 常见因子结构) |
| L0 截面(函数) | cs_Rank/cs_Demean/cs_Zscore/cs_TransNorm | 4 | 是(建议限顶层/近顶层, 避免频繁套嵌) |
| L1 扩展时序 | 其余 ts_*(RSI/SMA/EMA/WMA/BOLL/KDJ/MACD 等 talib 指标) | ~40 | 可选(扩展包, 前端勾选) |
| L1 派生字段 | IdioRet/Value/TotalRet | 3 | 可选(特殊场景) |
| L2 参数化基类/基础因子 | BASE_OPERATOR_MAP(rsi/adx/macd/kdj/bbands/ema 等 36 个) | 36 | **作为叶子节点入搜索(L2, 2026-08-16 已落地)**: 参数化基类带窗口池, 固定参数基类用引擎默认参数; 同时作 Warm-Start 初始基因(见下) |
| 财务 FN | FN(roe) 等 | 22 | 否(首版技术 GP 不纳入, 避免财务对齐口径混入) |
| 信号 ta_CDL* | K线形态信号 | 大量 | 否(IC 适应度不适合 0/1 信号因子) |

**L2 参数化基类 / 基础因子的入搜索方式(2026-08-16 收敛):**
1. 基类叶子(T_BASE_LEAF)以"叶子"身份嵌入树, **GP 不向基类内部注入子树**, 只可替换整片叶子或其窗口参数 —— 避免把"字段+算子的复合体"当函数节点导致树深 +1、参数域叠加、搜索空间爆炸, 也避免退化为"自动多因子合成"(与多因子页重复)。
2. 分两类: **参数化基类**(周期是参数, 带窗口池, 如 rsi[6,14,21]/sma/ema/wma/.../reversal/returns) 与 **固定参数基类**(参数固定=标准参数, 实例即基础因子, 如 adx/cci/willr/atr/macd/kdj/bbands/mama/sar 及 TALIB 族 22 个)。
3. 同时保留 **Warm-Start 初始基因** 身份: 初始种群按比例(如 30%)由"库内已有因子表达式(取 formula)随机变异"注入, 既利用已有知识, 又保持随机搜索广度。
4. 前端 GP 参数面板"搜索空间"下拉: L0 基础算子+字段 / L1 新时序算子 / L2 算子+基类; 基类叶子在 GPU 路径下已全部算子化且与引擎逐位对齐(见阶段4.1)。

**输入端好不好做 / 会不会太庞大(评估):**
- 首版 L0 空间 ≈ 8 字段 × 6 常数 × 7 算术 × 18 时序 × 4 截面, 树深 ≤4(节点数 ≤15), 窗口参数域 8 值 —— 完整组合理论上限极大, 但 GP 每代只需评估"种群大小"个候选(默认 60~100), 10~20 代 = 600~2000 次 `evaluate_expression`, 每次 ms 级, **CPU 分钟级可跑完**。
- CPU 路径计算瓶颈在 `evaluate_expression`(逐股 rolling)而非空间大小; 用股票池子集(30~50 只)+ 短区间(2~3 年)进化, 收尾用全池全区间精评 Top-N, 可进一步压耗时。
- **GPU 路径(阶段4.1, 已落地)**: 开启"启用GPU加速"后, 整树在 TensorPanel 上 torch 批量求值(一次建张量, 全树共享), 摆脱逐股 rolling, 大种群/长代数下吞吐显著提升; 搜索空间内算子已全部 GPU 化, 仅 warm-start 注入的库内公式 fallback CPU。
- 约束手段: 语法合法(`validate_expression`) + 深度/复杂度上限 + 表达式去重(规范化哈希) + 除以 0 / 负对数安全化(加小量/取绝对值)。

**回答用户三个疑问(2026-08-16 代码核实):**

> **Q1: 是不是所有算子都可以放进 GP?**
> 否, 必须分级 + 排除三类。
> 代码核实: `_SAFE_FUNCTIONS` 自动登记了全部 `ts_*`(约 60+)、`ta_*` talib 指标(约 40)、`ta_CDL*` K线形态(大量), 若全放进去, 终端/函数集规模直接上百, 组合空间天文数字且绝大多数候选无意义。
> - **排除 `ta_CDL*`**: 输出是 0/1 离散信号, IC 适应度(截面连续相关)不匹配, 且会让树变成"信号拼接"而非连续因子。
> - **排除 `FN(...)` 财务算子**: 财报期对齐口径(可用日=report_date+120天)与纯价量 GP 的评价管线冲突, 首版技术 GP 不纳入。
> - **排除高元/重算子**: `ts_Amplitude`(3字段)、`ts_Corr/ts_Cov/BETA`(双输入)、`ts_Chan*`/`ts_Dragon*`(缠绕/特殊)不作为首版搜索节点, 可作 L1 扩展开关。

> **Q2: 基础因子 / 参数化因子模板(基类)能不能加进 GP?**
> 能, 且已落地为**两种身份并存**(2026-08-16 收敛):
> 1. **基类叶子(主搜索身份, L2)**: 以 `T_BASE_LEAF` 叶子嵌入树, GP 不向基类内部注入子树, 变异只改窗口参数 —— 在"从原始字段发现新结构"的同时, 也允许 GP 直接产出"以某技术指标为组件"的因子; 参数化基类带窗口池, 固定参数基类用引擎默认参数。
> 2. **Warm-Start 初始基因(并行)**: 库内已有因子的 formula(如 `rsi(14)`、`-1*ts_Decay(...)`)按比例(30%)随机变异注入初始种群 —— 业界 AutoAlpha / Warm-Start GP(arXiv:2412.00896)共识: 纯随机初始化在"有效 alpha 稀疏"的空间效率极低。
> 注意: 基类不能当**函数节点**(对其再注入子树组合), 否则会退化为"自动多因子合成"(与多因子页重复), 失去"从原始字段发现新结构"的挖掘意义。

> **Q3: 都加进去会不会输入端太庞大复杂? 好不好做?**
> 分级控制后**好做**。裸数全体积看似大(11 字段 × 上百算子 × 36 基类), 但:
> - 首版只放 L0 受限子集(8 字段 + 6 常数 + 7 算术 + 18 时序 + 4 截面), 每代只评估种群大小个候选;
> - 窗口参数离散化(有限集合) + 深度上限 + 表达式去重, 把"可生成"压缩到实际可枚举量级;
> - 真正耗时在评价不在搜索, 用子池子区间进化可分钟级跑完;
> - 基类/财务/CDL 全都不进主搜索, 前端用"算子层级(L0/L1/L2)"开关逐级放开。

### 4.6.2 与 QuantGplearn 的对接差异(为什么不直接用它)

> **2026-08-17 修正(代码核实)**: 本节旧表述"QuantGplearn 用扁平计算、我们用简易算法"**只分别对应两个系统的旧路径** —— 当时对比的是 QuantGplearn 遗留 sklearn 路径与本系统 CPU 路径。QuantGplearn 本身有两条计算路径(见下), 本系统自阶段 4.1 起 GPU 路径为唯一主体, 计算方式已与 QuantGplearn 张量路径同构(详见 5.4.1)。

**QuantGplearn 自身的两条计算路径:**
- **遗留 sklearn 风格路径**(`SymbolicTransformer`): 基类继承 `BaseEstimator`, 函数签名是"扁平 X → 预测 y", 逐样本整体计算(`fitness.py` 用 `np.apply_along_axis(rankdata,...)` 整体秩) —— 即旧表述中的"扁平计算"。
- **GPU 张量路径**(`GpuSymbolicTransformer` + `TensorPanelData`): `_program.execute_tensor` 在 **[T, N, F] 三维张量**上整树求值, 截面算子沿标的维、时序算子沿时间维, 适应度用 `tensor_fitness.mean_rank_ic`(逐日截面 Spearman 均值) —— **不是扁平计算**。

**本系统的两条计算路径:**
- **CPU 路径(阶段 1~3, 历史实现)**: "字段面板 dict + 逐股 rolling → 因子面板", 自写简易求值(`evaluate_expression` + `run_ic_timeseries_panel` 逐股 RankIC) —— 即旧表述中的"简易算法", 与 QuantGplearn 张量路径计算方式不同。
- **GPU 路径(阶段 4.1 起, 当前唯一主体)**: `TensorPanel` + `PanelTensorCompiler` 整树张量化求值, 适应度 `mean_rank_ic` —— 与 QuantGplearn `execute_tensor` **同构**(见 5.4.1)。

**保留 QuantGplearn 的进化循环结构, 不引入其 sklearn/gplearn 依赖**(Py3.13 兼容存疑):

| QuantGplearn 概念 | 我们对应实现 |
|-------------------|-------------|
| `_Program`(LISP 树) | `lib/factor_gp.py` 自写表达式树(random_tree / expr_to_string) |
| `_Function(name, arity, param_type)` | `GP_SPACE` 元数据(函数名/arity/参数域) |
| 锦标赛选择 / 交叉 / 变异 / 精英 / parsimony / 早停 | `evolve()` 进化循环(逐代按 gplearn 概率分布) |
| `make_fitness`(pearson/spearman) | **GPU 路径**(当前主体): `mean_rank_ic`(QuantGplearn 张量语义, 见 5.4.1) — 整树 torch 求值后逐截面 Spearman 均值; **CPU 路径**(历史): `fitness_expr` → `run_ic_timeseries_panel` 的 RankIC |
| 逐股求值 vs 整树张量求值 | **GPU 路径**: `TensorPanel` + `PanelTensorCompiler` 在 [T,N,F] 三维张量上整树 torch 求值, 与 QuantGplearn `execute_tensor` 同构; **CPU 路径**: `evaluate_expression(expr, panel)` 逐股循环 |
| hall_of_fame + tolerable_corr 去冗余 | 阶段2 候选去冗余(`_redundancy_remove` 思路) |

## 6. 关于"ML 综合因子再入库合成"(Mega-Alpha)的合规路径

**问题**: 把 ML 综合因子 f(A,B,C) 存进因子库, 再用多因子页把 F 和 A,B,C 一起合成 g(A,B,C,F) —— 即"非线性映射嵌套非线性映射", 是否扭曲?

**结论**: 业界标准做法(称 Mega-Alpha), **不扭曲, 但有三个必须满足的前提**:

| 前提 | 原因 |
|------|------|
| ① 每个 ML 因子先做单因子 OOS 验证(IC/IR/分层) | ML 输出是拟合产物, 不过验证就入库 = 过拟合直接进生产 |
| ② 与库内其他因子去冗余(相关性>0.8 剔除) | 若 F 就是 A/B/C 的函数, F 与输入因子高度相关, 一起合成=重复计权(此即"扭曲"场景) |
| ③ 捕捉增量信息(与已有因子低相关) | 非线性映射若与线性因子完全冗余则无增量价值 |

**实现**: 多因子页已有 `_redundancy_remove`(Spearman>0.8) + 单因子评价入口, 前提①②自动满足。因此: ML 综合因子经单因子评价、确认 OOS 有效且低相关后, 与其他因子一起纳入多因子合成是**合理且业界标准**的。

- [x] 性能: 进化期用股票池子集(30~80 只)× 短区间(2~3 年), 收尾精评 Top-N 用全池全区间。

### 阶段 1.6 实测验证记录 — CPU 路径 (2026-08-16, 真实数据回归)

> 阶段 1 交付后, 用 PostgreSQL 真实行情跑了一遍端到端测试(40 只 2023~2025 全覆盖 A 股, 训练 2023-01~2025-02 / 测试 2025-02~2025-12, 种群 36 / 代数 12 / 深度 4 / 持有期 5), 暴露 3 个问题并验证 1 个关键优化方向:

**问题 A(严重): 规模因子主导** —— 最佳候选是裸字段 `Amount`(成交额=规模代理), 训练段 |RankIC|≈0.126。A 股训练段小市值/小成交额效应极强, 无中性化时 GP 必然收敛到规模因子, 挖不出有增量信息的复合因子。候选去重后仅 3 个, 全是 `Amount` 变体。
**问题 B(严重): 候选多样性差 / 早熟收敛** —— best fitness 在 gen3 即停滞(0.109→0.126), 精英保留(10%)+ 锦标赛选择导致种群同质化, 触发早停(8 代 vs 计划 12 代)。
**问题 C(中等): 搜索空间薄** —— 候选以裸字段/简单变换为主, L0(8 字段+16 时序+4 截面, 无派生字段)对"组合出有深度结构的新因子"支撑不足。

**已验证优化方向(市值中性化适应度)**: 在适应度评估里接入 `run_ic_timeseries_panel(..., marketcap_proxy_lookback=20)`(点-in-time 成交额代理, 引擎已内置)后:
- `Amount` |IC| 0.126 → 0.044(规模干扰被压制);
- `(cs_TransNorm(Amount)-ts_Decay(Amount,5))` 0.116 → 0.010(Amount 的线性组合被完全吸收, 暴露其无增量);
- 技术类因子(动量/乖离/波动等) IC 基本保持。
=> **市值中性化适应度是让 GP 去挖"非规模信号"的关键开关**, 已列为 P0 落地下一步。

**与 QuantGplearn 的对比结论(2026-08-17 注: 该结论针对当时的 CPU 路径)**: 本实现 CPU 路径与 gplearn 家族在进化机制(ramped half-and-half / 锦标赛选择 / 子树交叉 / 点变异 / 精英 / parsimony / 早停)上高度同构; 差异在"表达式执行复用安全 DSL(逐股循环)+ 函数集更受限 + 适应度用 RankIC + 内置 Warm-Start"。**其中的"表达式执行"差异已于阶段 4.1 消除**: GPU 路径改用整树张量化求值(`PanelTensorCompiler`), 计算方式与 QuantGplearn `execute_tensor` 同构(见 5.4.1)。共同短板(规模因子主导 + 早熟收敛)为 GP 通用问题, 原版同样存在。

**核心差异结论**: 本实现与 gplearn 家族在**进化机制**(ramped half-and-half / 锦标赛选择 / 子树交叉 / 点变异 / Hoist / 精英 / parsimony / 早停)上高度同构; 差异集中在 **"表达式执行复用安全 DSL + 搜索空间分层(含基类叶子) + RankIC 适应度 + 内置 Warm-Start/市值中性化/多样性奖励/OOS 复核/GPU"** 这些量化落地增强上。gplearn/QuantGplearn 本身不解决"规模因子主导 + 早熟收敛"这两个 A 股 GP 通用问题, 本实现已通过市值中性化 + 多样性奖励缓解(未根治, 见 5.4.3)。

### 5.1.1 Warm-Start 可解析化 (阶段5.1 附项, 2026-08-17 用户决策)

> **状态: ✅ 已完整落地 (2026-08-17)**。本节"问题背景"为改造前的历史缺陷描述(均已解决); 设计目标(完全同质)由「解析器 + 白名单 + 折叠注入」达成, 详见文末"落地记录 / 验证结论 / 实施状态"。

**问题背景 (代码核实):**

1. **warm 注入个体以字符串原子注入**: `{"t":"field","name":formula,"_warm":True}`(factor_gp.py L758), 深度=1。
2. **`crossover` 深度1短路 (L489)**: `if tree_depth(child)<=1 or tree_depth(donor)<=1: return child` —— warm 原子既**不能作为 donor 把叶子嫁接到普通树**, 也**不能被拆解成内部算子重组**。其真实命运只有三种: 原样复制(缓存命中)、被 subtree_mutation 整体替换、被 point_mutation 展开成普通字段。
3. **warm 因子作用退化为**"独立起点候选": 评估后进 `hall_of_fame` 收尾直接输出, 保证候选起点不差于因子库; 但**不承担"基因注入/构件遗传"职责** —— 无法把库内因子的内部算子构件拆出融入搜索空间。
4. **GPU 兜底误判隐患**: `gpu_supported` 对 `field` 节点只查 `t=="field"` 返回 True, **不校验字段名是否在 GPU 字段表**(factor_gpu_evaluator.py L404-405)。若未来出现含未知字段名的树(如 warm 公式字符串作字段), 会误判"可 GPU 化" → 进 `PanelTensorCompiler.compile` 遇 `_field_pos` 缺字段抛 ValueError(L318-319) → `_eval_one_gpu` 吞异常返回 `fitness=None` → 该树被当**无效个体淘汰**, 而非回退 CPU `evaluate_expression` 递归求值。
5. **`evaluate_expression` 本身是递归分层求值**(factor_engine.py L4791+, AST 叶子字段/基类 → 逐层算子), 具备计算"任意可解析复合表达式"的能力; 问题只在**公式未被解析成 dict 树**。

**设计目标 (用户决策):**

> warm start 注入的因子**必须能够被解析**, 形成与随机树一致的 dict 树结构, 从而:
> - 内部算子可被交叉/变异**拆解重组** (真正的构件注入)
> - 可作为多节点 donor 参与**子树交叉** (嫁接/拆解)
> - **GPU 整树求值可覆盖** (tree 非 None, 不再走字符串 fallback)
> - **完整实现遗传算法相关功能**

**双途径 (并行推进):**

| 途径 | 内容 | 处理对象 |
|------|------|----------|
| **A. 注入前筛选 (白名单)** | 只注入"可解析且可 GPU 化"的公式; 筛掉含财务(`FN()`)/信号(`ta_CDL`)/其他坏字段, 或含 GPU 不支持字段/算子的公式 | 因子库 formula 列表 (routes 构造 warm_start_formulas 处) |
| **B. 补充搜索空间** | 对"仅含技术字段但缺算子/缺 GPU 支持"的公式, 把缺失的算子/字段**补入搜索空间** (`SPACE_L0/L1/L2` + `TORCH_ARITH/TS/TS_RAW/CS` 算子表), 使其可被随机树使用并可 GPU 化 | 搜索空间定义 + GPU 算子表 (factor_gp.py / factor_gpu_torch.py) |

**核心前置: 字符串公式 → dict 树 解析器 (`formula_to_tree`):**

- 覆盖语法: 字段 / 常数 / 算术算子(add/sub/mul/div/abs) / 单参带窗时序(`ts_*(X,N)`) / 无窗时序(`ts_Log`) / 截面(`cs_*`) / 基类叶子(`returns(N)`/`rsi(N)`/`atr(N)` 等, → `base_leaf`) / **多参多字段 `ts_*` 折叠为现有 base_leaf(2026-08-17 新增, 见审计结论表)** / 负号 / 括号优先级。
- 输入: 因子库 formula 字符串; 输出: factor_gp 的 dict 树。
- 与引擎 `validate_expression` 词法/语法语义对齐(复用其安全校验, 但产出树结构而非直接求值)。

**落地步骤:**

1. 实现 `formula_to_tree` 解析器 (lib/factor_gp.py 或独立模块)。
2. 实现 `formula_parseable_gpu(formula)` 检查 = 解析成功 + `gpu_supported(树)`。
3. routes 构造 `warm_start_formulas` 时: 逐条筛选(途径A), 解析成树后注入 `evolve`(注入树而非字符串)。
4. `evolve` warm 注入改: 注入 dict 树(非 field 原子), tree 非 None → 可 GPU 编译、可交叉拆解、可作 donor 嫁接。
5. 搜索空间审计(途径B): 枚举因子库技术类公式的算子/字段, 对照 GPU 支持集; 缺的补入 `GP_TS_OPS`/`TORCH_TS` 等(如需新增 torch 算子)。
6. 修复 GPU 兜底: `gpu_supported` 的 field 分支**校验字段名是否在 GPU 字段表**; 未知字段/未覆盖算子 → 返回 False → 树回退 CPU `evaluate_expression` 递归求值(不再误判判死)。

**边界与注意:**

- 可解析但 GPU 未覆盖的公式(如含 `np.maximum`/比较运算符): 途径B 评估是否补 torch 算子; 不补则走 CPU 回退(语义一致, 已由 `mean_rank_ic` 同口径保证)。多参/多字段 `ts_*` **不走此路径** —— 已折叠映射为现有 base_leaf(见审计结论表, 2026-08-17)。
- 纯坏字段(财务/信号): 途径A 直接筛掉, 不进入搜索空间。
- 目标态: 注入的每棵 warm 树与随机树**同构**, 完整参与遗传算法; 落地后 warm start 才真正承担"基因注入/构件遗传"职责。

### 5.2.5 残差正交化实现记录 (2026-08-17)

**设计目标**: 将 `dedup_by_corr` 的相关阈值剔除升级为"新因子与已选因子池逐截面回归取残差后再判增量", 比纯相关阈值更严格保证增量 alpha (来源: Auto-Alpha-Finding, sw0843)。

**实现方式 (可选增强, 默认关闭, 关闭时零行为变化):**

- `lib/factor_gp.py`:
  - `dedup_by_corr` 新增参数 `ortho_mode`(默认 False)、`min_incremental_ic`(默认 0.01)。
  - `ortho_mode=True` 时, 在对每个候选做相关剔除后, 额外对候选相对"已保留因子池"做逐截面 OLS 回归取残差 (复用 `numpy.linalg.lstsq`, 与 `neutralize_regression` 同款无 statsmodels 依赖), 计算残差因子面板的增量 RankIC (`_panel_rank_ic_mean`); |增量IC| < `min_incremental_ic` 时视为"相对已选池无增量信息"而剔除。
  - 新增 `_panel_residualize(fv, pool_panels)` 辅助函数: 逐截面 OLS 回归取残差, 返回残差面板。
  - 新增 `_panel_rank_ic_mean(fv, prices_panel, ...)` 辅助函数: 面板 RankIC 时序均值 (与主循环 `mean_rank_ic` 同口径)。
  - `evolve` 新增 `ortho_mode`、`min_incremental_ic` 参数, 透传 `dedup_by_corr`。
  - 候选保留者字典新增 `incremental_ic`、`ortho_pool_size` 字段。
  - 报告新增 `ortho_mode`、`min_incremental_ic`、`incremental_ics` 字段; 剔除记录新增 `reason="low_incremental_ic"` 类型。
- `routes/factor.py`:
  - `_run_gp_pipeline` 读取 `orthogonalize`(默认 False)、`min_incremental_ic`(默认 0.01) 参数, 透传 `evolve`。
  - 返回结果新增 `orthogonalize`、`min_incremental_ic` 字段。
  - `params` 记录新增对应字段。
- `templates/factor.html`:
  - GP 参数面板新增"残差正交化(增量IC)"复选框 + 条件显示"增量IC阈值"输入框。
  - 去冗余报告显示区分正交化模式 vs 常规模式。
  - 剔除列表显示区分 `low_incremental_ic` 原因 vs 常规相关剔除。
  - 候选入库 description 记录增量IC与池大小(入库形态: 存原始表达式 + 记录投影操作信息)。

**入库形态**: 因子库中始终存原始表达式(expression), 正交化投影操作不写入公式; 增量IC 信息记录在入库 description 中, 供因子库详情溯源。

**验证:**

- 合成面板测试: `ortho_mode=False` 行为与历史完全一致; `ortho_mode=True` 正确计算增量 IC, 正确剔除低增量候选项。

### 5.2.7 PCA-QD 多样性引导实现记录 (2026-08-17)

**设计目标**: 把 Jaccard token 新颖性奖励升级为 PCA 特征空间距离奖励(新奇性搜索), 把"语法相似"判多样性升级为"行为相似"判多样性, 引导搜索远离已探索区域 (来源: AutoAlpha, arXiv:2002.08245)。

**AutoAlpha 原版机制**: 因子行为相似度 = 逐日截面相关均值 `sim(i,j)=mean_t corr(a_i,a_j)`; 用 PCA 把每个因子值矩阵 [T,N] 压缩为主成分 score 时序(复杂度 O(N)->O(pT)); 新 alpha 与"档案库"中已发现者相似度过高(如 corr>0.9)则降权/拒绝。

**实现方式 (可选增强, 默认关闭, 关闭时零行为变化; 与 Jaccard 共享锦标赛选择钩子):**

- `lib/factor_gp.py`:
  - 新增 `_factor_behavior_desc(f)`: 因子值矩阵 [T,N] 列中心化后取前 3 个主成分的时间 score 时序, 按日期降采样 8 段, 拼成 [24] 行为描述子 (torch SVD, 无 sklearn 依赖)。
  - 新增 `_fit_pca_projection(X, n_comp)`: numpy SVD 去均值 PCA 投影。
  - `evolve` 新增 `pca_qd`(默认 False): True 时评估期在 `_eval_one_gpu` 免费缓存行为描述子, 每代 `_pca_diversity_scores` 对"种群+跨代档案库"描述子做 PCA 投影, 以 k=5 近邻平均距离(PCA 特征空间距离)作为新颖性, 归一化到 [0,1] 后复用 `gen_div_weight` 进入锦标赛选择; 描述子不足时自动回退 Jaccard。
  - 新增跨代档案库 `_pca_archive`(有界 300, 保高适应度+多样行为, 超限按最旧优先淘汰); 返回报告新增 `pca_qd`、`pca_archive_size` 字段。
- `routes/factor.py`: `_run_gp_pipeline` 读取 `pca_qd`(默认 False)透传 `evolve`, `params` 记录新增字段。
- `templates/factor.html`: GP 参数面板新增"PCA-QD多样性(行为空间)"复选框, 请求与状态恢复同步。

**验证:**

### 5.2.8 replacement 防早熟 + hierarchical 分层搜索实现记录 (2026-08-17)

**设计目标**: 针对"有效 alpha 稀疏、纯随机 GP 效率低"的两类收敛问题 (来源: AutoAlpha, arXiv:2002.08245):

1. **replacement 防早熟**: 种群更替段对"新生个体"与"已入下一代个体"做 token Jaccard 相似度检查, 相似度 >= 阈值的同质个体被**变异再生**(替换为多样化变体), 防止种群被少数高适应度同质基因统治导致早熟收敛 (AutoAlpha 相似度红线 0.9)。
2. **hierarchical 分层搜索**: 粗搜(受限算子集 L0, 快、覆盖主流结构) → 取粗搜 Top-N 候选 → 细搜(扩展算子集 space_level, 深度探索)以粗搜候选作 **Warm-Start 基因**, 平衡搜索广度与深度。

**实现方式 (可选增强, 默认关闭, 关闭时零行为变化):**

- `lib/factor_gp.py`:
  - `evolve` 新增 `replacement_thresh`(Optional[float], 默认 None=关闭): 在"生成下一代"循环里, 对每个新生个体(交叉/变异/reproduction 产物)遍历 `new_pop` 已入个体做 `_token_similarity`(token Jaccard), 最大相似度 >= 阈值时对该个体再做一次 `point_mutation` 变异再生, 替换掉同质新生个体, `replacement_count` 累加统计; 返回报告新增 `replacement_thresh`、`replacement_count` 字段。
  - `evolve` 新增 `fitness_mode`(str, 默认 "rank_ic"), 透传 GPU 求值上下文与 `fitness_expr`/`_eval_one_gpu`, 供任务 9 使用。
- `routes/factor.py`:
  - `_run_gp_pipeline` 读取 `replacement_thresh`(<=0 或 >=1 视为关闭, 默认 None)、`hierarchical`(默认 False)、`fitness_mode`(白名单 rank_ic/rank_icir/long_short_sharpe, 默认 rank_ic)。
  - 新增 `_run_evolve_once(space_lvl, warm_f, warm_t)` 内部函数封装单次 `evolve` 调用; `hierarchical=True` 时先粗搜 `_run_evolve_once("L0", ...)` 取粗搜 Top-12 候选解析为 dict 树(可 GPU 整树求值), 再以之作细搜 Warm-Start 基因执行 `_run_evolve_once(space_level, ...)`; 返回结果新增 `hierarchical`、`hier_coarse_candidates`、`hier_coarse_curve`、`hier_coarse_best_fitness`、`hier_fine_warm_count` 字段供前端展示两阶段信息。
  - `oos_recheck` / `walk_forward_recheck` / `permutation_significance` 同步透传 `fitness_mode`, 保证训练段/测试段/WF/permutation 全链路同口径。
- `templates/factor.html`:
  - GP 参数面板新增 "Replacement防早熟" 复选框 + 条件显示 "同质阈值"(0.5~0.99, 默认 0.9); "Hierarchical分层搜索" 复选框; "适应度目标" 下拉(rank_ic / rank_icir / long_short_sharpe)。
  - `runGp` 请求体透传 `replacement_thresh`、`hierarchical`、`fitness_mode`; `savePageState`/`loadPageState` 纳入 `gpReplacement`/`gpReplacementThresh`/`gpHierarchical`/`gpFitnessMode` 持久化与恢复。

**验证 (端到端, 真实数据 2024-01~2025-06):**

- 场景1 CPU 全开 (hierarchical=True, replacement=0.85, long_short_sharpe): 返回 `hierarchical=True`、`hier_coarse_candidates=11`、`hier_fine_warm_count=11`、`fitness_mode=long_short_sharpe`, 正常产出 5 个候选。
- 场景2 CPU 默认路径 (hierarchical=False, replacement=None, rank_icir): 单次进化, 与历史行为一致, `hierarchical=False`。
- 场景3 GPU 全开 (hierarchical=True, replacement=0.85, rank_icir): GPU 整树求值路径下分层搜索 + 防早熟 + 适应度目标全链路通过。

### 5.2.9 适应度合成扩展 (ICIR/Sharpe) 实现记录 (2026-08-17)

**设计目标**: 默认适应度为 RankIC 均值(抗噪弱、只判方向强弱), 扩展为多目标选项 (来源: QuantGplearn tensor_fitness.py / GinkGO 策略3):

- `rank_ic`(默认, 原行为): 全样本逐日截面 Spearman RankIC 均值。
- `rank_icir`: IC 均值 / IC 标准差 (抗噪, 关注 IC 稳定性; 对齐 QuantGplearn `rank_icir`, 无偏)。
- `long_short_sharpe`: 每日截面 top-k 做多 / bottom-k 做空 组合净收益夏普 (对齐 QuantGplearn `long_short_sharpe`: quantile=0.3、fee=3e-4、annualization=252)。

**实现方式 (默认 rank_ic, 关闭时零行为变化):**

- `lib/factor_gpu_evaluator.py`:
  - `mean_rank_ic` 新增 `fitness_mode` 参数: `rank_icir` 分支 = `mean(IC)/std(IC)`(clamp ±100); `long_short_sharpe` 分支 = 每日截面因子 top/bottom 30% 各持 0.5 毛多头/空头, 净收益减去换手成本后 `mean/std*sqrt(252)`。
  - 修正做空端选股: 多空两端均基于**因子预测值**选股(top-k 做多 / bottom-k 做空), 而非"空头用 target 选股"(原实现会让无信号时组合夏普异常偏高); 收益来源仍为 target。
  - `_rank_2d` 增加 torch < 1.13 兼容(不支持 `argsort(stable=True)`, 降级普通 argsort, 秩序在无平局时一致)。
  - `batch_mean_rank_ic` / `batch_mean_rank_ic_exprs` 同步透传 `fitness_mode`。
- `lib/factor_gp.py`: `evolve` 的 GPU 求值上下文与 `fitness_expr` 透传 `fitness_mode` (白名单外回退 "rank_ic")。
- `routes/factor.py`: `_run_gp_pipeline` / `oos_recheck` / `walk_forward_recheck` / `permutation_significance` 全链路透传。
- `templates/factor.html`: "适应度目标" 下拉 + 持久化 (见 5.2.8)。

**验证 (合成数据, torch 1.11 + CUDA):**

- 有信号 (factor 预测 target): rank_ic=0.82、rank_icir=16.75、long_short_sharpe=126.5。
- 无信号 (噪声 target): rank_ic=0.02、rank_icir=0.18、long_short_sharpe=3.0 (修正前异常高达 186)。
- 反向信号 (factor 反向预测): long_short_sharpe=-73.4 (方向正确)。
- 语义正确性: 有信号 > 无信号, 反向为负。

## 8. 关键实现要点(与现有代码的对接)

1. **表达式引擎复用**: 
   - **CPU 路径(fallback)**: 候选因子直接用 `lib/factor_engine.py` 的表达式解析/执行, 保证与因子构建页/因子库完全一致, 不另起评估器;
   - **GPU 路径(当前主体)**: `lib/factor_gpu_torch.py` 提供对应 torch 算子(与引擎语义逐位对齐), `PanelTensorCompiler` 编译表达式树为 torch 函数, 整树求值无需 fallback; 不支持的算子 fallback 到 CPU 路径。
   - 无论 CPU/GPU, 表达式语法与算子语义均与引擎一致。
2. **字段/算子空间**: 从 factor_engine 算子表(`ts_*`/`rank`/`returns`/`amplitude` 等) + 因子构建页 DSL 抽取, 按 4.6 分级作为 GP 的终端集与函数集。
3. **防泄漏**: 候选评价用分时段(walk-forward 风格)IC, 只用历史数据, 避免未来函数; 标签=未来 N 日收益。**(CPU/GPU 路径同规则)**
4. **评价复用**: 复用 `factor_evaluator` 的 IC/分层/含成本绩效; JSON 返回统一经 `_json_safe_response` 清洗。**(CPU/GPU 路径同规则)**
5. **入库复用**: `upsert_factor`(含软删除激活规则, is_custom 区分); evaluation_type 用 `_is_technical_ts_expression` 启发式自动标记。**(CPU/GPU 路径同规则)**
6. **与多因子页不重复**: 挖掘页不做"特征诊断/ML 合成"(多因子页已有), 只做"表达式空间搜索生成新因子"。**(CPU/GPU 路径同定位)**
7. **GP 内核自写**: `lib/factor_gp.py`(表达式生成器/进化循环/适应度封装)已建成, 进化流程参照 gplearn/AutoAlpha(锦标赛选择/子树交叉/点变异/精英), 表达式与适应度复用现有引擎, 不引入 gplearn/deap 依赖。**(CPU/GPU 路径共享内核逻辑)**
8. **适应度口径**: 
   - **GPU 路径(当前主体)**: `mean_rank_ic`(QuantGplearn 语义, 逐日截面 zscore + 逐截面 Spearman RankIC 均值), 与 QuantGplearn `tensor_fitness` 对齐;
   - **CPU 路径(fallback)**: 直接用 `run_ic_timeseries_panel(factor_values, prices_panel, rebal_period, ...)` 拿 RankIC 均值/ICIR/分层作为适应度与候选展示口径, 与单因子评价一致。
9. **GPU 整树求值(阶段4.1, 已落地)**: `lib/factor_gpu_torch.py` 提供 torch 算子库(含 L2 基类叶子全部算子, 与引擎逐位对齐); `lib/factor_gpu_evaluator.py` 用 TensorPanel 一次构建 `[T,N,F]` 张量、PanelTensorCompiler 把表达式树编译为 torch 求值函数, 适应度用 `mean_rank_ic`(QuantGplearn 语义); 未 GPU 化算子 fallback 到 `evaluate_expression`; `factor_gp.evolve(use_gpu_tensor=True)` 与后端 OOS/WF `use_gpu` 开关接入, 无 CUDA 自动回退 CPU。
